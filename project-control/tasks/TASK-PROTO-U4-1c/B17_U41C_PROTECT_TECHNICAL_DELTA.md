## 4. Concurrency design and ordering

Retain `domainTransaction` identity/session/user/tenant/department and GE workspace ordering. After authorization, acquire one transaction-scoped advisory exclusive lock keyed by a **domain-separated canonical full UUID tuple** `(kind, server-bound tenant, resource UUID)`: for `initiative` the resource UUID is the **library initiative ID** (`client_initiatives.initiative_id`), never the selection row ID; for `requirement` it is the requirement ID. Concrete scratch design: PostgreSQL `pg_advisory_xact_lock(hashtextextended($1, 0))` with a single bound text parameter formatted `u41c-protect:v1:<kind>:<lowercase-canonical-tenant-uuid>:<lowercase-canonical-resource-uuid>`, kind closed to `initiative` or `requirement`. Both UUIDs must have the exact validated 8-4-4-4-12 hex-and-hyphen syntax, lowercased before concatenation, including DB-returned IDs; no whitespace, short form, braces, URN, missing value or raw request-derived key is accepted. This is lock-key canonicalization only: keep existing input validation and tenant mismatch behavior, do not loosen them. Full UUIDs and fixed separators/kinds prevent string aliasing; hash collisions can still occur and mean extra serialization only, never authorization. Different tenant UUIDs produce different pre-hash keys but are not promised distinct 64-bit hashes. A service ID, user ID, department ID or selection row ID never enters the initiative key. All writers use the same derivation and checked-out connection. Advisory locks are not row security: recheck tenant, department, linked service, selection and parent after waiting, in the same transaction. Under READ COMMITTED reread in a new statement after the lock; fail closed on missing/changed scope. Pin/verify isolation and implementation in scratch; STOP if function availability/privilege or key parity fails.

Order: session → user → tenant/department → workspace if present → **one** canonical anchor → scoped parent/status → evidence row → audit → commit. No path in this unit acquires both the old selection-ID anchor and the natural-key anchor or two resource anchors; do not lock a child row or unique/FK-mutating row before the anchor. If a future operation truly needs two anchors, STOP for a separately reviewed total ordering rather than introducing it here. Multipart parsing precedes the final transaction, which must revalidate. Avoid waiting on external work while holding locks.

* W POST and DELETE derive tenant from fresh `domainTenant` and the library ID from their already validated parameter; perform existing linked-service, eligibility and freeze checks, take the common natural-key lock **before** POST's unique INSERT or DELETE's selection lookup/mutation, then rerun scope-dependent eligibility/freeze and selection checks after waiting. Preserve existing outcomes and transaction-bound audit. The POST anchor exists even when no selection row exists.
* E status PATCH initially performs an RLS-scoped plain SELECT by the request's selection row ID and `access.tenantId`, retrieving `id, client_id, initiative_id`. Verify own employee department and server-bound tenant; if no row, retain existing inaccessible/not-found refusal. Take the `initiative` natural-key lock using the returned initiative ID, then in a fresh statement reread **the same original selection ID plus tenant plus initiative ID**, linked eligibility and department before touching status. A concurrent delete/reselect creates a different selection ID: do not silently redirect the stale request to the new row; refuse through the existing not-found path, with no write.
* For initiative evidence upload/delete, first read the RLS-visible status and its selection via a join binding `status.department_id` to own department and `selection.client_id` to server tenant; retain original status ID, selection row ID and library initiative ID. Acquire the same natural-key lock, then reread and revalidate all three IDs, tenant, department, linkage and evidence parent before acting. If the row disappeared or was replaced, use existing scoped refusal; do not redirect to a new selection or infer a missing parent's identity. Document evidence continues to use the requirement anchor with equivalent scoped revalidation. W sees same-tenant status dependencies under its actual SELECT policy, but never relies on W `FOR UPDATE` visibility or an E selection UPDATE grant. RLS/ACL and join feasibility are scratch acceptance obligations.

For PATCH: caller supplies non-negative integer `expectedVersion`; 0 means caller observed no row, ≥1 means the observed row's revision. After the anchor, find the row with full scoped key. If observed/current mismatch, reject with existing 409 `version.conflict` vocabulary and safe `{error, code, conflict:{expectedVersion: current, providedVersion: supplied}}`, instruct refresh/review, no foreign content or attempted values. Missing version uses baseline 400 `version.required`. A successful create stores 1; a successful update matches ID + current version and increments once with the audit in the same transaction. Only the first of two requests carrying the same expected revision succeeds; no implicit retry, merge, or overwrite. Version changes on every successful status PATCH, including note-only. For an E list response, add a scalar `ownVersion` on each visible requirement or selected initiative: 0 when its own department has no row, otherwise that row's revision; add revision to each existing scoped submission/status object and successful PATCH. W/C/P do not receive another department's `ownVersion`; their existing authorized arrays may include each returned row's revision. Authorize before revealing even revision/existence. Guard integer range and overflow without wrapping or changing data; an unexpected exhausted revision aborts and is reported for separate disposition, not silently reset.

Delete vs submit: submit commits first → delete rereads the stamped parent and returns existing `evidence.locked`, with no file/audit change. Delete commits first → its removal/audit commit before submit can enter; submission then follows its normal version/state checks. Failed/rolled-back transaction has no success acknowledgment and does not block the other from succeeding. Evidence upload before unselection makes the status/evidence dependency visible; if unselection wins while there is no status, subsequent creation must recheck and fail without writing. Upload and delete against a live status serialize on its anchor; append after submit remains valid. Whether evidence-only mutations should increment the parent's edit revision is **not assumed**; they do not rewrite status fields, and submit/delete safety comes from the anchor. Test and review this boundary.

The parent lock is advisory, not a DB constraint against nonparticipating writers. FK RESTRICT is the independent DB backstop for every existing status (including drafts) and avoids an RLS-blind count/insert race. A same-tenant associated file necessarily has a status under the healthy model; pre-existing orphans break this implication and require G2. RESTRICT may refuse client/library ancestor deletion as well; department/client direct cascade and standalone evidence remain outside the request-path guarantee and must be inventoried, not presented as solved. Do not claim all possible parent deletions are safe.

## 5. FORCE RLS, security and error compatibility

`b17-content.sql:798–805,889–933`: selection SELECT is tenant/linked; E has no selection UPDATE policy; status E UPDATE is own department; W can read same-tenant department statuses; evidence SELECT is tenant scoped and E department scoped. `SELECT FOR UPDATE` requires suitable privileges and RLS UPDATE visibility. The reported surrogate measurements in §2 support the candidate advisory lock but explicitly show E selection/requirement and W status row locks cannot be assumed. Real routed transactions and deployed principal/ACL equivalence remain unverified. Do not add an E selection UPDATE policy to make a lock work. A conditional update with scoped predicates is an alternative only if it preserves the identical serialization proof.

W's dependency check must observe all same-tenant statuses under actual FORCE RLS and separately associated evidence with tenant bound; a hidden/ambiguous result is never 'no dependencies'. Check row counts for all departments, mismatched tenant links and orphan inventory under an explicitly authorized scratch/operator inspection role, never widen a request predicate or return a foreign count. RESTRICT protects hidden statuses even when W's count is incomplete. Existing request checks, fixed parameterized SQL, 404/403 isolation, fresh identity, audit and no raw SQL diagnostics remain mandatory.

`evaluations.ts:244–280` uses `version.conflict` / `version.required` with conflict data; `approvalChain.ts:149–195` maps missing or noninteger versions to **400**, mismatch to **409**. The following are design envelopes, not implemented responses. Owner §13 approved the two Arabic strings exactly and requires the existing baseline for missing version; status/code and minimized conflict fields are technical choices:

* Missing/noninteger revision: HTTP 400 `{"error":"A version is required to save (optimistic locking). Reload the item and retry.","code":"version.required","conflict":{"expectedVersion":<authorized current revision or 0>,"providedVersion":null}}`, using the exact existing `evaluations.ts:275` message rather than inventing another. Negative/out-of-range revisions must fail safely without an additional invented visible message; confirm compatibility with baseline in scratch.
* Stale revision: HTTP 409 `{"error":"تغيّرت البيانات منذ فتحها. يرجى تحديثها ومراجعة التعديلات قبل الحفظ.","code":"version.conflict","conflict":{"expectedVersion":<authorized current revision or 0>,"providedVersion":<valid supplied revision>}}`. As in the existing evaluation contract, `expectedVersion` is the **server's current** revision; return it only after full resource authorization, and do not return foreign values, snapshots or attempted text.
* Scoped unselection dependency: HTTP 409 `{"error":"لا يمكن إلغاء اختيار المبادرة لوجود بيانات أو مرفقات مرتبطة بها.","code":"initiatives.dependency"}`. This is analogous to existing `documents.dependency` 409, without its instruction to remove a reference. Only issue after authorization and positive same-tenant dependency proof or a specifically identified FK refusal; no counts, IDs, department names or SQL diagnostics. Preserve existing document/evidence/initiative lock codes and other denial precedence. Verify exact UTF-8 response and UI display on scratch; no new reopen or deletion workflow.
